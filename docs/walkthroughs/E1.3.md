## 1. The dedup rules, restated (Contract 7, `deduplication:` block)

```yaml
key: [cruise, station_id, event_id, latitude, longitude, sample_datetime_utc]
coordinate_tolerance_deg: 0.001   # ~100m
rules:
  1. DOMES families ([02][03][04] + parents [09][10]): dedupe by
     cruise+station/event+coords+date, NOT DOI.
  2. NOAA<->PANGAEA mirrors: prefer the record with clearest methods;
     retain both provenance links.
  3. Individual nodules ([05]) nested within box-core EVENTS ([01]):
     the event is the spatial sample.
  4. Regional grids ([18][19]): label compiled/interpolated; never
     merged with observed stations.
  5. Image cover/count != recovered mass: never merged; never converted.
```

One gap noted, not blocking: rule 1 references DOMES "parents `[09][10]`," but neither
source_id exists in `source_queue.yaml`'s 13 entries. Not fatal — the rule is a generic
key-match, not something needing those specific IDs hardcoded — but flagged for
awareness.

## 2. Four decisions made with the engineer of record before writing code

| # | Question | Decision |
|---|---|---|
| 1 | Survivor precedence when two rows are duplicates? (Contract only says "prefer clearest methods" for the NOAA/PANGAEA case — not operationalizable; no rule at all for DOMES-family.) | **Highest `quality_grade` wins** (A>B>C); ties (the common case — E1.2's normalizers set one grade per evidence class, not per source) go to first-encountered. |
| 2 | `[05]` individual nodules nesting in `[01]` events — drop or aggregate, and where? | **Aggregate in a new `[05]` adapter** (`NoduleAggregateAdapter`), not in dedup — a many-to-one reduction doesn't fit `Specification`'s one-observation boolean contract. | 4 | Dedup key lists 6 fields — what if one row has a field blank that the other has filled (e.g. one DOMES source reports only `station_id`, no `event_id`)? | **Null-tolerant per field**: a blank on either side never blocks a match; a real disagreement between two non-null values does. Coordinates always use the tolerance radius, never exact equality. |

## 3. Architecture

```
    corpus_builder.build_corpus()
        │
        ├─ build_boxcore_adapter()          [01] PangaeaAdapter    ─┐
        ├─ build_nodule_aggregate_adapter() [05] NoduleAggregateAdapter │  each through
        ├─ build_dryad_chamber_adapter()    [06] TabularFileAdapter  │  IngestionPipeline
        └─ build_ts6_grid_adapter()         [18] RegionalGridAdapter ─┘  .run(), SAME
                                                                          shared corpus +
                                                                          registry + dedup

    IngestionPipeline.run():
      fetch -> adapt -> normalize -> validate -> dedup -> append
                            │            │         │
                            │            │         └─ DuplicateStationSpecification(corpus)
                            │            │            (SPECIFICATION; live reference to
                            │            │             the same corpus list -- this is
                            │            │             what makes idempotency and
                            │            │             cross-adapter dedup both work)
                            │            └─ Observation(**record)  (Pydantic; schema v4)
                            └─ NormalizerRegistry (E1.2, unchanged)
```

`DuplicateStationSpecification` (rules 1 & 2 — mechanically identical, one class serves
both) holds a **live reference** to the corpus list `IngestionPipeline` appends into.
That's the whole trick: checking a new candidate against "the corpus so far" naturally
makes (a) cross-source dedup work (source B's pipeline runs after source A's, so A's
accepted rows are already visible) and (b) idempotency work (re-running the same
adapter against the same corpus sees its own previously-accepted rows). No change to
`IngestionPipeline._dedup()` was needed — it's still the exact stateless filter from
E1.1/E1.2; the Specification does its own bookkeeping (see `_link_provenance`, which
replaces a corpus entry in place via `.model_copy()` when the earlier arrival wins).

Rules 4 & 5 aren't separate `Specification` classes — they're a single guard,
`_comparable_evidence(a, b) = a.evidence_class == b.evidence_class`, since a single
box-core event's own MASS+COUNT+COVER rows legitimately share every dedup-key field
(same event, same coords, same date) and must NOT be treated as duplicates of each
other. Requiring the same evidence_class blocks GRID-vs-observed (rule 4) and
COVER/COUNT-vs-MASS (rule 5) as a side effect, while still correctly allowing GRID-vs-GRID
or MASS-vs-MASS matching — which idempotency for a GRID source specifically depends on
(see §5's bug).

Rule 3 (`[05]` nesting) has **no Specification at all** — see decision #2. By the time an
aggregated `[05]` row reaches dedup, it's already one row per event; there's nothing
left to nest.

## 5. A frozen-contract bug found while building this (schema v3 -> v4)

Not one of the two planned stop-conditions — surfaced mid-implementation, while writing
the "flagged rows are retained" test. `docs/contracts/master_observations.schema.json`
set `abundance_kg_m2`'s own field `maximum: 45` — **identical** to
`normalization.yaml`'s screening ceiling. That meant any value the screening step should
flag (`qa_status="flagged"`) instead failed Pydantic validation first (`le=45` rejects
it outright), so "never silently dropped" (CLAUDE.md, normalization.yaml) could never
actually hold for this one field. The four grade fields don't have this problem —
`mn_pct`'s Pydantic bound is `le=60` against a screening max of `45`, deliberately wider,
so flagging works correctly there. `abundance_kg_m2` was the one field where someone set
the hard bound exactly equal to the soft one.

Confirmed with the engineer of record: widened `abundance_kg_m2` to `le=100` (schema
`v4`), matching the headroom pattern the grade fields already had.
[`test_flagged_row_from_screening_is_retained_with_qa_status_intact`](../../tests/test_corpus_builder.py)
now proves a `60 kg/m2` reading (over the 45 screening max, under the new 100 field max)
actually reaches the corpus with `qa_status="flagged"` rather than raising.

Not touched: `Proposals and contract V3/Contracts_v3/master_observations.schema.json`
(the original authoring copy outside the canonical `docs/contracts/` location) still
shows `maximum: 45` — left alone since it's your source document, not something read by
any code path.

## 6. A test-fixture mistake, caught and fixed before it shipped

`so268_nodules_sample.csv`'s first draft reused `[01]`'s exact event IDs and coordinates
(plausible — both are SO268 companion datasets). Running the full corpus build then
showed `[05]`'s MASS rows vanishing: `DuplicateStationSpecification` correctly recognized
`[01]`'s box-core MASS reading and `[05]`'s aggregated-nodule MASS reading of the *same*
event as duplicates (same key, same evidence_class) and dropped the second one arriving.
Arguably defensible behavior in general, but it obscured what this corpus build was
supposed to demonstrate (that `[05]`'s aggregation works), so the fixture now uses
distinct events/coordinates (`SO268-5_x-1` instead of `SO268-1_x-1`) — cross-source dedup
is exercised precisely in `test_dedup_rules.py` instead, with hand-built `Observation`s.

A second, more consequential bug from the same debugging pass: `_comparable_evidence`'s
first draft excluded GRID from matching **anything**, including another GRID row.
Idempotency broke immediately — re-running `build_corpus()` against an already-populated
corpus added 3 duplicate GRID rows instead of recognizing them, because no GRID row could
ever be found "comparable" to any other GRID row. Fixed by simplifying to "same
evidence_class," full stop (§3) — which correctly implements rules 4 and 5 *and* allows
GRID-vs-GRID matching, with no special case needed.
[`test_two_grid_rows_at_the_same_cell_still_dedupe_against_each_other`](../../tests/test_dedup_rules.py)
locks this in.

## 8. Deliberately missing / out of scope

- **GRADE station join** (`join_tolerance_km`) — explicitly out of scope per instruction.
  No GRADE-carrying source (`[19]` Washburn) is wired into `corpus_builder.py` yet, so no
  GRADE rows appear in this corpus at all; when `[19]` is wired later, `GradeNormalizer`
  (E1.2) already passes GRADE rows through unjoined, as instructed.
- **Intra-batch duplicate detection.** `DuplicateStationSpecification` only catches a
  candidate that duplicates a row *already in the corpus* (from an earlier adapter in
  `REAL_ADAPTER_BUILDERS`, or an earlier call to `build_corpus()` against the same list).
  Two duplicate rows arriving in the *same* adapter's own single fetch would not catch
  each other. None of the four wired sources' sample data has that shape today.
- **Two known-but-unenforced edge cases in the key match:** (a) DOMES "parents `[09][10]`"
  (§1) don't exist as registered sources; (b) two rows with *every* key field null and
  coordinates within ~100m would be treated as duplicates purely on proximity — considered
  low-risk (real cruise data almost always carries a cruise/date) and documented in
  `dedup_rules.py`'s module docstring rather than guarded against.
- **`[05]`'s real column names are a placeholder.** `so268_nodules_sample.csv`'s shape
  (`Event`, `Nodule mass wet [g]`, ...) is a plausible guess pending Track G confirming
  the actual PANGAEA.904962 columns.

## 9. Review follow-up: D1 (merge-on-dedup) + D4 (symmetric provenance), 2026-07-27

Two bugs in the original E1.3 survivor logic, found on review:

- **D1 — data loss on merge.** The loser was discarded outright, taking any field it
  carried that the survivor lacked with it. On real data this bites exactly at `[05]`
  vs `[01]`: `[05]`'s aggregated nodule MASS row carries `mean_nodule_mass_g`; `[01]`'s
  box-core MASS row never does. The old tie-break (equal `quality_grade` ->
  first-encountered) meant whichever one was ingested first silently won, and if that
  was `[01]`, `mean_nodule_mass_g` was gone — the exact field `CountNormalizer`'s
  row-only gate (E1.2) depends on.
- **D4 — one-directional provenance.** `_link_provenance()` only ran when the row
  already in the corpus won. When the candidate won on higher `quality_grade`, the old
  code did `corpus.remove(existing)` with no link recorded at all — rule 2's "retain
  both provenance links" held in one direction only.

Both share one code path now, `_merge()`, called from `is_satisfied_by()` regardless of
which side wins:

```
survivor = candidate if quality(candidate) > quality(existing) else existing
merged = _merge(survivor, loser)   # D1: gap-fill only, never overwrites a non-null
                                    #     survivor value
                                    # D4: notes + duplicate_group_id record the
                                    #     loser's source_id/source_record_id either way
corpus[index of existing] = merged
return False   # always -- the corpus slot already holds the final row;
               # the pipeline's own append step must not add anything else
```

**A consequence worth knowing:** `is_satisfied_by()` now returns `False` on *every*
duplicate match, including the direction where the candidate wins (previously it
returned `True` there, relying on the pipeline's normal append to add it).
`DuplicateStationSpecification` now always writes its decision straight into the corpus
list itself, then tells the pipeline "don't also append this" — the false-means-drop
contract with `IngestionPipeline._dedup()` is unchanged, but false no longer means
"nothing happened to the corpus." One existing test
(`test_higher_quality_grade_survivor_replaces_lower_quality_existing`) needed updating
for this — not a regression, just this contract becoming explicit.

5 new tests in `test_dedup_rules.py`: gap-fill in both insertion orders (completeness
must not depend on arrival order), merge-never-overwrites (a disagreeing non-null value
on the loser is discarded, not substituted in), and provenance recorded in both
directions (existing-wins and candidate-wins).

`test_corpus_builder.py`'s idempotency and byte-identical-CSV tests were re-run, not
assumed — both still pass. `_merge()` is deterministic (fixed iteration over
`Observation.model_fields`, `sorted()` donated-fields list), and re-generating
`data/corpus/master_observations.csv` produced byte-identical output to before D1/D4,
since none of the four currently-wired sources actually collide with each other (that
collision is exercised only in `test_dedup_rules.py`'s hand-built cases).

## 10. Review follow-up: D3 (GRID same-source dedup only), 2026-07-27

`_comparable_evidence()`'s "same evidence_class is enough" rule (§3/§6) was too
permissive across sources: `[18]` TS-6 and `[19]` Washburn are independent compiled
products, and two grids covering the same cell are two independent estimates worth
comparing, not two observations of one sample. Fixed: GRID additionally requires the
same `source_id` to match another GRID row — non-GRID evidence classes are unaffected
(cross-source dedup is the whole point for observed stations, rule 1). One new test,
`test_grid_rows_from_different_sources_never_dedupe_even_at_the_same_cell`; the existing
GRID-vs-GRID idempotency test (`test_two_grid_rows_at_the_same_cell_still_dedupe...`,
same `source_id` in both rows) needed no change — it already covered the case D3
preserves. The end-to-end idempotency test was re-confirmed green.

## 12. Review follow-up: D8 (cross-dataset reconciliation, `[01]` vs `[05]`), 2026-07-27

Both PANGAEA files are now real and describe the SAME 36 box-core events:
`[01]` PANGAEA.904967 (the authors' own published per-event aggregate) and `[05]`
PANGAEA.904962 (individual nodules, aggregated by `NoduleAggregateAdapter`). This is a
genuine cross-check between two independently-published datasets — and it also revealed
that D1's merge was already firing silently between them (same 36 events, same
evidence classes MASS/COUNT) before this review, with no one having decided who wins.

**`[01]`'s real columns** (64-line metadata block, 36 rows): `Event | Date/Time |
Latitude | Longitude | Elevation [m] | Depth sed [m] | Nodules [#] | Nodules [#]
(buried) | Nodules size [cm**2] (median nodule size) | Nodules m [kg] (total) | Nodules
[%] (seafloor coverage by nodules)`. Three parameters share the name "Nodules",
disambiguated only by full header string — a substring match would silently misroute a
cover percentage into a mass field.

**A/B/C implemented** — new [`boxcore_summary_adapter.py`](../../engine/prospectivity/ingestion/boxcore_summary_adapter.py)
(`BoxcoreSummaryAdapter`, a thin `PangaeaAdapter` subclass): reads the real file via the
same header-terminator detection `[05]` uses (factored into a new shared
[`_pangaea_tab_format.py`](../../engine/prospectivity/ingestion/_pangaea_tab_format.py)
rather than duplicated); correct column mapping (`Nodules m [kg] (total)` -> MASS,
`Nodules [#]` -> COUNT, `Nodules [%] (seafloor coverage by nodules)` -> COVER); negated
`Elevation [m]` -> `water_depth_m`; `cruise` derived from the event label prefix; COVER
rows get a `notes` entry recording it's measurement-derived (summed ellipsoidal nodule
footprint / corer area), not image-derived — the hard rule (never `abundance_kg_m2`) is
unchanged. The same "failed" header flag D5.3 established for `[05]` is re-applied
independently here (`[01]`'s own header carries the identical COMMENT) — necessary
because `_merge()`'s gap-fill only fills null fields, and `qa_status` is never null, so
it would NOT have propagated from a dropped row to a surviving one.

`derivation_formula` in `mass_normalizer.py`/`count_normalizer.py` now **appends**
rather than overwrites, so `NoduleAggregateAdapter`'s own adapter-level aggregation note
(mass sum is measured-only; `mean_nodule_mass_g` divides by weighed count) survives
normalization instead of being silently replaced by the later `abundance_kg_m2`-derivation
text.

**D — reconciliation** (new [`test_reconciliation.py`](../../tests/test_reconciliation.py),
comparing `[01]`'s raw adapter output against `[05]`'s, before any dedup merge):
`nodule_count` matches exactly for **31/36 events**; `nodule_mass_kg` agrees within
**0.285kg** (the observed max, not a round number — `[01]` rounds to 1 decimal, `[05]`'s
individual masses are 5g-quantized by the recording equipment itself); `[01]`'s
`mass*4` lands in the published 11-27 kg/m² CCZ band for every event. **5 residual
count events**, not the 4 anticipated going in —
`SO268/1_15-3 (+1), SO268/2_95-2 (+2), SO268/2_140-1 (-6), SO268/2_175-1 (-1),
SO268/2_205-2 (+16)` — `SO268/2_205-2` was found while writing the test (its 16
unweighed "Plus N" nodules aren't in `[01]`'s published count, unlike the other 11
"Plus N" events, where they mostly are) and verified against both raw files before
being reported, not silently folded into "close enough." The tolerance was NOT loosened
to make it disappear.

## 14. Review follow-up: P2 (D8-F MASS order-dependence, and a false comment), 2026-07-27

**Comment fix.** `boxcore_summary_adapter.py`'s F comment claimed setting `[01]`'s
MASS/COUNT `quality_grade="A"` made survivorship "deterministic... independent of
adapter run order." False for MASS, confirmed by the audit's reordering test. Corrected
to state plainly: that line alone only ever guaranteed COUNT's determinism (only `[05]`
gets `CountNormalizer`'s "B" default); MASS determinism depends on a cross-file
invariant this same review adds in `nodule_aggregate_adapter.py`.

**Behavior fix.** `[05]`'s aggregated MASS record now gets an explicit `quality_grade=
"B"`, on scientific grounds: it's a sum of *measured* nodules only, structurally
excluding every unweighed sub-5g nodule (D5.1 — up to 60% of an event's population) and
quantized to the equipment's 5g floor, whereas `[01]`'s published total covers every
nodule, weighed or not. `[05]`'s MASS is the less complete measurement of the same
quantity; the D1 merge resolving deterministically is a consequence of that being true,
not the reason for saying so.

**The guard test** (`test_mass_and_count_survivors_are_identical_regardless_of_adapter_order`,
`test_corpus_builder.py`) runs the real `build_corpus()` twice — normal and reversed
`REAL_ADAPTER_BUILDERS` order — and asserts the published CSV is byte-identical either
way, plus a targeted source_id check. Required a small testability addition to
`build_corpus()` itself (`adapter_builders` parameter, defaulting to
`REAL_ADAPTER_BUILDERS`) so the test exercises the real production path rather than a
re-implementation that could drift from it. **Verified by mutation**: temporarily
removed the `quality_grade="B"` line, confirmed the test fails (byte diff at a MASS/COUNT
row), restored it, confirmed green.

**The general problem, reported not implemented.** Today's tie-break — highest
`quality_grade` wins, ties go to first-encountered — resolves ties by
`REAL_ADAPTER_BUILDERS` list position, which is exactly the bug this task fixed for
`[01]`/`[05]`. It is NOT fixed for future collisions: normalization.yaml's own rule 1
(DOMES families `[02][03][04]` dedupe by key, not DOI) and rule 2 (NOAA/PANGAEA mirrors,
"prefer the record with clearest methods") both describe sources that are *expected* to
collide, and none of them have a natural quality-grade asymmetry the way `[01]`/`[05]`
did — MASS-class sources all default to `quality_grade_default: A` per Contract 7,
identically. When any of these are wired in, they will tie, and resolve by list order
again, silently.

Two options, not implemented:

- **Lexicographic `source_id` tie-break.** Trivial, fully general, no contract change —
  but scientifically arbitrary. It would make the corpus reproducible regardless of
  build-script edits, but "src_domes_fewkes1980" beating "src_domes_piper1979"
  alphabetically has nothing to do with which is the better record, and for rule 2
  specifically it would systematically ignore the contract's own stated
  "clearest methods" criterion in favor of alphabetical order.
- **Explicit precedence read from a contract.** Add a `preference_rank` (or similar)
  field to `source_queue.yaml`, filled in by Track G per colliding family — this is the
  literal, direct implementation of rule 2's "prefer the record with clearest methods,"
  not a proxy for it. Requires: a `source_queue.yaml` version bump (contract change,
  needs sign-off + a `docs/contracts/README.md` note per CLAUDE.md); real geology
  judgment for every currently-known colliding family before it's useful; a restructured
  tie-break in `dedup_rules.py::is_satisfied_by` (today's `if candidate_rank >
  existing_rank: candidate wins else: existing wins` conflates true ties with existing
  outranking candidate — a third branch is needed); `DuplicateStationSpecification`
  loading the new field the same way it already loads `coordinate_tolerance_deg`; new
  tests for at least one simulated multi-source collision family, not just `[01]`/`[05]`.

Recommendation if asked to implement: precedence-from-contract is the only option that
actually satisfies rule 2's own language, with lexicographic order as the *documented
fallback* for any pair Track G hasn't ranked yet (rather than blocking dedup entirely)
— and the merge's existing `notes` mechanism already has a natural place to record
"unranked, used fallback tie-break" for future audit visibility.
