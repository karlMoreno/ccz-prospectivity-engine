## §1 — What the block records, and how it is resolved

`economics` (one new `RunManifest` field, default `None`, `SCHEMA_VERSION`
2 → 3 — HASH.1's rule honoured: a None default, refused at class definition
otherwise):

| key | content | resolved from |
|---|---|---|
| `scenarios[]` | name, **the cutoff in the `DeclaredField` shape** (value, units, `data_origin`, `author`), grade metric, confidence levels, the computed origin, the per-reason verdict | the manifest's own `economic_results` |
| `rasters{}` | per file: kind, scenario or pair, estimator, z, **sha256 recomputed from the bytes**, counts/area, the two reasons' lifted states | **E4.2's association record**, verified against the file's bytes AND tags AND the manifest's results |
| `difference_fraction_of_predictable` | per pair → estimator → z | the manifest's `economic_differences` |
| `association` | the record's file and **its sha256** — the record the block resolved from is hashed into the chain | the bytes |
| `n_files` / `n_footprint_rasters` / `n_difference_rasters` | 20 / 12 / 6 | counted against the directory |
| `watermark_note` | two independent reasons with SEPARATE expiry conditions | — |

**The record is verified, not trusted.** `_verify_economics` compares, for
every raster, five records of each fact by name (`_require_equal`): the
bytes' sha256 vs the record's; the raster's TAGS (kind, scenario(s),
estimator, z) vs the record vs the manifest's result; `n_minable` (or
`n_only_b`) **recomputed from the pixel values** vs the tag vs the record vs
the result; the origin **recomputed by `combine_origins`** over the surfaces'
computed origin and the cutoff's declared origin vs the tag vs the record vs
the result; and the terrain reason's lifted state **re-derived from the
stack's declared DEM origin** vs the record vs the result. The directory
listing, the record's entries and the results' `raster_file` names must be
the same set (18), each way named. Then the association record and the
origin sidecar are hashed into `output_hashes` under `economics/<basename>`
— one constant relative component, never a run directory — so the record
the block resolved from is a link the chain HAS.

**The instrument note.** E-M6 is the project's pattern at its purest: a
verification that reads a value from one carrier and compares it to two
others looks like recomputation and is copying, and no test can see it
until the carriers are forged to agree. The fixture is the only observer.
And its first draft "caught" the mutant by erroring on the real code — a
catch that is not one, recorded because the rule "a mutation that fails
for an unexamined reason is a survivor" (E4.1's B-M5) applied here
verbatim, and the harness's summary line is what showed it (`1 failed` on
the real code before any mutation).

None of the other six needed hand re-application; every report named the
