**Assembly, plus the thing that leaked, stated.** The prompt expected "an
entry point, an output path, a registry choice, and the manifest write.
Nothing else." The inventory found that the composition's two INPUT seams
had only test-fixture implementations — PATTERNS.md §3.2 had carried
`TerrainSource` and `TS6Reference` at 0 production impls since Phase 0 —
so the full pipeline could run only from inside a test. The rule for this
was already written at the E1.4 plot entry point ([plot_stack.py:3](../../engine/prospectivity/features/plot_stack.py)):
*the DEM is passed in, this module never generates one and never imports
`tests.*`*. So the two classes added are the thin production halves of the
seams — a path plus the CALLER'S DECLARED ORIGIN; hash and pixel size read
from the bytes and the geotransform; CRS must already be EPSG:4326; an
undeclared or unknown origin refused at construction — and the synthetic
inputs stay test-generated and are passed in:

```bash
python -c "from pathlib import Path; from tests.fixtures.rasters import *; \
  write_synthetic_bathymetry(Path('inputs/dem.tif')); write_synthetic_ts6_raster(Path('inputs/ts6.tif'))"
python -m engine.prospectivity.harness --dem inputs/dem.tif --dem-data-origin SYNTHETIC \
  --ts6 inputs/ts6.tif --ts6-data-origin SYNTHETIC --out runs/<name> --run-id <id>
```

declaration (`MEASURED` / `DERIVED`) — the substitution the seams exist for.

## §2 — Commit 2: the three manifest additions (adversarial review)

Schema 3 → 4 under HASH.1's rule: one new field, `None` default, refused
at class definition otherwise. **Both historical hashes held** — measured
before the change and pinned after, by literal, in two tests.

### 1. The full-data fit — `surfaces[est].full_data_fit`

The estimator's `provenance()` at the full-matrix fit, for every estimator.
Kriging's is the whole `KrigingReport`: `range_km` **21.611 km**,
`range_at_candidate_ceiling` **True**, `range_below_first_supported_lag`
False, `residual_dof` 1, the bin table the fit saw with every excluded bin
and its reason, the spherical alternative, and the `range_km_reported`
sentence. RF's is `validation_facing_fields()` (500 trees, five importance
seeds, `max_samples_leaf=None` — read back). The baseline's is its mean and
sd. An estimator whose provenance is empty is refused by name.

**What separates this from the per-fold record.** The test refits a FRESH
`OrdinaryKrigingEstimator` on the matrix — not the object that wrote the
record, not a walkthrough — and requires the whole dict equal; then asserts
the recorded range is not any fold's range. Mutation N1 (copy the last fold's
provenance) fails with `n_training: 28 != 35` and a different nugget — a
fold fit is visibly a fold fit.

**A fact the record made visible in the fixture itself:** conftest's
`surface_assembly` builds the surfaces with a 100-tree forest while the
extension module cross-validates with the 40-tree light registry, so in that
fixture `full_data_fit.n_estimators` reads 100 where every fold reads 40.
Two registries in one composition is exactly what the engine refuses
(`cv_runner.registry is not estimators`) and the harness cannot produce; it
is pinned in the test so it stays seen rather than absorbed.

### 2. `sd_min` / `sd_max` — beside `mu_min` / `mu_max`

In `SurfaceResult.summary()`, so the sidecar's `surface` block and the
manifest both carry them. Production values: kriging sd [3.332, 5.031], RF
[2.000, 5.200], the baseline constant 3.881. Recomputed in the test from the
written uncertainty raster's pixels; separated from the mu range (N2, sd
from mu: `19.53 ≠ 3.88`).

### 3. `training_stations` — the new field

```text
  training_stations:
    n: 35 · coord_columns: [longitude, latitude] · station_ids: [... the matrix's order ...]
    coordinates: {<station_id>: [lon, lat]}          ← from the TrainingMatrix OBJECT the run was built on
    data_origin: MEASURED                             ← the CORPUS's (combine_origins over admitted rows)
    matrix_sha256: …                                   ← the ids and coords are INSIDE it
```

The viewer never re-implements the training gate against the CSV. The
origin is the corpus's, kept apart from the run's (SYNTHETIC — the
covariates'); N4 (copy the run origin) fails `SYNTHETIC != MEASURED`.

**Deliberately no emitter cross-check against `cell_groups`.** The station
ids and coordinates are inside `matrix_sha256`, which the emitter already
recomputes from the arrays and compares against the matrix manifest and the
base; a check below that guarantee would be the unreachable-check
sub-pattern (CLAUDE.md's coverage-that-isn't, ×2) — no test could reach it,
because the chain refuses first. The ground truth sits OUTSIDE the record
instead: the same `CorpusCsvSampleSource` by ID (`Station.from_observation`,
which is `source_record_id`), and the raw corpus CSV by coordinate, read as
strings with no Pydantic and no gate in the path (rule 2).

## §3 — Commit 3: the run directory as a product

Stated in `harness.py` as `RUN_LAYOUT` (the diagram above it) and asserted
against the DIRECTORY LISTING both ways: every file under `<out>` is the
root record, a member of `output_hashes` under the key the layout states, or

exists with its bytes. Resolution is checked from the record: each surface's
rasters and sidecar via `surfaces[est]`, each economics raster via the

### Is any of this committed? — No, and what it would take

Not intended: the viewer and the API read a run directory the harness (or
E5.6's CI job) produces, not one under `data/`. The questions E5.0 §5 raised
were answered by PROBING rather than reasoning — the production run staged
at `data/runs/e5.5-probe/` in a `git archive` copy of the repo, `git add`ed
so `git ls-files -- data` walks it, `audit()` called directly:

| direction | result |
|---|---|
| (1) as written | **refused, three ways.** UNCLASSIFIED ×10: `economics/economics.footprints.json` (no top-level `data_origin`) and the nine `features/stack/` files (the stack has no sidecar; its `provenance.json` is not a marker form). INVALID ×18: every economics raster `AUTHORED with author None` — the `author_inherited_from` gap (BACKLOG §3, E4.2 approval), now confirmed on a real run directory. **NEW:** `run_manifest.json` flagged as "newly carrying `author: unrecorded`" — it QUOTES Contract 4's cutoff declaration (`economic_results[].cutoff.author`, four occurrences) and the deep scan reads a quoted declaration as a new use |
| (2) one sidecar entry stripped (`ordinary_kriging_prediction.tif`) | exactly that raster becomes UNCLASSIFIED; nothing else moves — the sidecar association works by name |

So committing a run directory requires (a) a declaration for the association
record and the stack (a top-level `data_origin` block; a `data_origin.yaml`
in `features/stack/`), (b) Karl's `author_inherited_from` decision, and (c)
a rule for QUOTED declarations in the deep unrecorded scan — a manifest that
records another file's `author: unrecorded` is not a new author. BACKLOG §3
carries (a) and (c) in one entry with the trigger the E3.1+2 and
`author_inherited_from` entries already share: before any run output is
committed under `data/`.
