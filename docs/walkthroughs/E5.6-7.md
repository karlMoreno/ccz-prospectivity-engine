## §1 — E5.6: the named, artifact-producing job

**Tripwire:** the job adds exactly the expected shape — the synthetic
inputs written by the suite's own generator and passed in DECLARED, the
harness with ITS OWN DEFAULTS (the production registry; all four designs)
twice in two trees, a verification step, an upload named `run-<sha>` with
30-day retention and `if-no-files-found: error`. No `needs` on `test`: the
artifact's own gate is the verify step. Nothing leaked.

**`verify_run` runs the machinery**, re-implements nothing: the API's own
loader (self-hash, EXTENDED, every named file present), every output file's
bytes against `output_hashes` (52), the corpus and feature-stack links by
substance, E2.5's guard RE-RUN per design with its failing **and** passing
sets compared to the committed expectation, and with `--same-as` the
two-tree identity on the job's own machine. **The job is not a gate on the
verdict:** it succeeds on a refusing run and fails only if the sets MOVE —
the day CP1/CP4 land, `EXPECTED_VERDICT_SETS` is updated deliberately.

**The known limits, so a red job is diagnosed:** a run built on another
machine may differ in raster bytes (GDAL) — reaching every raster hash and
the sidecars and exports that quote them — and in `inputs.environment`,
which is inside the run hash by design; neither is substance.
`--environment` prints the block. The cross-machine comparison is a
deliberate command on the downloaded artifact (`verify_run <local>
--same-as <ci>` will report the moved hashes by name); what CI's GDAL
actually is, and which hashes it reaches, is measured the first time the
job runs — **pending the push.**

A finding while writing the test: **nothing had ever parsed `ci.yml`** —
PyYAML refuses the original `run: pip install … --only-binary=:all:` line
(a trailing `:all:` reads as a mapping), which GitHub's parser accepted.
Two block scalars, and the suite now parses the workflow it depends on.

## §2 — E5.7 commit 1: the deployment

**Where:** one host for both, because the API already serves the page
(same-origin, no CORS surface). The image is provider-agnostic
(`Dockerfile`: `python:3.11-slim`, the same wheel-only install, the pinned
run copied from `deploy/run/`, `uvicorn … --factory`); the candidates with
cost and uptime are in `deploy/README.md` (Fly.io ≈ US$2–3/mo; Render
US$7/mo to stay warm — the free tier's cold start would look like a
connection failure; a small VM ≈ US$4–6/mo). **The provider account,
billing and DNS are Karl's.**

**What run it serves:** the CI artifact `run-<sha>`, downloaded into
`deploy/run/` (gitignored) and baked into the image labelled with the SHA;
`run_id: ci-<sha>` and the content hash are served at `/runs`, the record's
bytes at `/manifest`, every file's ETag is its recorded hash. **Serving is
not committing** holds: nothing enters `data/`.

**Sentry — declined**, with the question answered: no failure identified
that uvicorn's logs and the viewer's three designed no-run states do not
already report.

**What the URL claims:** a preview card runs no JavaScript, so the verdict
banner cannot survive into it. The page's `<title>` and `description` /
`og:` tags carry the STANDING status in plain text (non-scientific until
Checkpoints 1/3/4; the verdict is on the page) — asserted by the
deployment check — and must be updated the day the facts change (the CP5b
entry's trigger). What a card cannot carry: the failing precondition by
name, the per-layer reasons, the hatch.
