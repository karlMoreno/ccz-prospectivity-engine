## Check 1 — georeference linearity: BLOCKED, and the scales are not plate carrée

**The residual measurement cannot run.** The render the script consumes,
`ts6fig/f38_hi-080.png`, is absent from disk, and **no renderer is installed** —
`pdftoppm`, `pdftocairo` and `gs` are all missing. Per the task's own instruction I
did not substitute a different rasterizer (PyMuPDF is present but is a different
engine, and the georeference constants are poppler-specific) and did not estimate
positions from `ts6_fig38_digitized.png`, which is a downsampled *output* preview.
**STOP on this check only.** BACKLOGged.

**Consequence to state plainly:** the sidecar records finding **11 vertical and 5
horizontal** graticule lines while pinning **2 per axis** as anchors, so **9 vertical
and 3 horizontal interior lines** are available as residual checks — and none of
them has been evaluated. The task's gate (*"if the maximum residual exceeds one
output cell, the recorded `digitization_method` is wrong"*) is therefore
**unevaluated, not passed.**

**What did run — the two axis scales, from the committed sidecar:**

| | anchors | scale |
|---|---|---|
| x | 754.5 px @ −160.0° → 4017.5 px @ −110.0° | 3263.0 px / 50° = **65.2600 px/deg** |
| y | 736.5 px @ +20.0° → 2127.0 px @ 0.0° | 1390.5 px / 20° = **69.5250 px/deg** |

**Ratio y/x = 1.06535** — the y axis is **6.54% larger per degree**.

**Plate carrée predicts exactly 1.00000.** It is not plate carrée. Solving
`acos(1/1.06535) = 20.17°`: the figure is an **equirectangular projection with a
standard parallel near 20°N** — which is the map's own northern edge. That is a
coherent map, not a defect.

**And the script handles it correctly anyway.** It fits **separate linear x and y
scales**, which is exactly right for equirectangular. So the *arithmetic* in
`digitization_method` is correct and its *projection name* is loose — "plate carree"
names the special case (standard parallel 0°) rather than the projection actually
used. Recorded as a wording imprecision, **not** a contract amendment: no number
changes, and the recorded method still re-runs to the same result.

## Check 2 — the nodata seam: a defect, with an unidentifiable cause

| | |
|---|---|
| affected column | **149** |
| longitude span | **−145.10 … −145.00** (cell centre −145.05) |
| valid cells | **3** (rows 52, 54, 57 → lat 14.75, 14.55, 14.25) |
| neighbours 148 / 150 | 73 / 77 (mean **75.0**) |
| **cells lost** | **72.0** |
| **as a fraction of the raster's 29,252 valid cells** | **0.246%** |

**Why the closing bridged every other graticule and not this one: not determinable
from the committed artifacts.** The obvious hypotheses were tested and all fail:

- **It is not the graticule-on-a-cell-boundary geometry.** 5° / 0.1° = 50 cells
  exactly, so **every** vertical graticule line falls on an output-cell boundary.
  All eleven are geometrically identical in that respect.
- **It is not the sampling-window width.** Column 149 gets a 6-px window, but so do
  **236** other columns, whose median valid count is 74.
- **The seam is not even on the line.** The −145° graticule sits at render px 1733.4,
  inside column **150**'s window (px 1733–1739) — and column 150 is **full at 77**.
  Column 149 samples px 1727–1732, entirely west of it.
- **No other graticule column shows any depletion at all.** Checked all eleven:
  −155 (53 vs 53/54), −150 (66 vs 67/67), −140 (76 vs 76/76), −135, −130, −125,
  −120 — every one flat.

So something occupies render px 1727–1732 that does not occupy the equivalent strip
at the other ten lines, and **identifying it requires the render** — the same
blocker as Check 1. **The fix is therefore not confined to an identifiable
parameter**, and nothing was applied. Recorded as a known defect with location and
magnitude, and BACKLOGged behind the same render dependency.

## Check 3 — upper-tail truncation

| class | cells |
|---|--:|
| <1 | 1,034 |
| 1–5 | 12,557 |
| 5–10 | 12,803 |
| 10–15 | 2,402 |
| **15–20** | **456** ← highest populated |
| 20–25 · 25–30 · 30–35 · >35 | **0 · 0 · 0 · 0** |

**Highest populated class 15–20 (midpoint 17.5). Four legend classes carry zero
cells.** The source's own tabulated grid-block maximum is **44.1 kg/m²** (TS-6
Table 5). The digitized surface tops out at **17.5** — it reaches **40%** of the
source's tabulated maximum.

**Statistics, with their weighting stated:**

| | value | weighting |
|---|---|---|
| raster mean | **5.887** | area-weighted over 29,252 cells of 0.1° |
| raster maximum | **17.5** | — |
| TS-6 Table 5 mean | 6.72 | over **grid blocks** |
| TS-6 Table 5 maximum | 44.1 | over grid blocks |

**Which comparisons survive the weighting difference:**
- **The maximum does.** An extremum is weighting-independent — no reweighting of
  cells can produce a value the surface does not contain. **17.5 vs 44.1 is a real
  truncation**, not an artefact of how the two are averaged.
- **The mean does not.** 5.887 vs 6.72 mixes truncation with the cell-vs-block
  weighting difference and cannot be attributed to either. It is reported, not
  interpreted.
- **No distribution-shape statistic survives**, for the same reason.

**The binned median is deliberately omitted.** With five populated classes the
raster's median is necessarily a bin midpoint (it would land on 5–10's 7.5), so it
reports the binning, not the source distribution. Recording it as a comparison
statistic against TS-6's 5.47 would be comparing a construction artefact to a
measurement.

> **Consequence for the honesty surface, which is where this belongs and not only in
> the sidecar: this benchmark cannot validate predictions above 17.5 kg/m² in
> EITHER DIRECTION.** It has no cells there. A prediction of 25 kg/m² has nothing to
> agree or disagree with; the surface's silence above 17.5 is absence of coverage,
> not evidence of a low value.

## Check 4 — masking validation: the nesting argument holds

The committed script masks red at line 64: `redpal = np.array([LEGEND[7][1],
LEGEND[8][1]])`.

- **In the red mask:** `30-35` (rgb 230, 83, 57) and `>35` (rgb 219, 37, 45).
- **Not in the mask:** `<1`, `1-5`, `5-10`, `10-15`, `15-20`, `20-25`, `25-30`.
- **The adjacent unmasked class, `25-30`: 0 cells.** So is `20-25`: **0 cells**.
- Contiguous empty run below the mask: `20-25`, `25-30`, `30-35`, `>35`.

> **THE NESTING ARGUMENT.** Filled-contour classes nest. A genuine region in `30-35`
> or `>35` must be enclosed by a `25-30` ring, which must itself be enclosed by a
> `20-25` ring. **Both rings are empty everywhere on the surface.** A region in a
> masked class therefore could not have been a genuine fill, and the radius-7
> opening removed **annotation only**.

This **replaces** the visual justification recorded in the sidecar (*"the figure
shows no red fill"*), which rested on a judgment about the printed page. The
argument above rests on the committed histogram and holds without looking at the
figure at all.

## Check 6 — eastern-limit corroboration for the [18]/[19] linkage

**"Open-year" is [19]'s own distinction, and its metadata states it outright.**
`Data Sheet 3_[19].xlsx`, Metadata sheet:

> "Nodule Abundance (kg/m2) obtained from **ISA, 2012 (2009 year)** and
> **proprietary information (2018 year)**"

So the **2009-year subset is the open-year subset**. Both subsets were measured
rather than assuming which was meant:

| | n | eastern limit |
|---|--:|---|
| [19] **Year 2009** (ISA, 2012 — open) | 2,364 | **−119.25** (cell centre; 0.5° grid → eastern cell edge −119.00) |
| [19] Year 2018 (proprietary) | 426 | −112.25 |
| **[18] this raster, valid data** | 29,252 cells | **−118.80** |

| separation from the raster's −118.80 | degrees | km at 15°N |
|---|--:|--:|
| **vs Year 2009 (open)** | **0.450** | **48.4** |
| vs Year 2018 (proprietary) | 6.550 | 704.3 |

Edge to edge the gap is smaller still: [19]'s easternmost 2009 cell ends at −119.00
against the raster's −118.80 — **0.20°, about 21.5 km**. Either way the two surfaces
stop **within less than one of [19]'s own 0.5° grid cells** of each other, while the
proprietary subset stops 704 km away.

> **RECORDED AS GEOMETRIC CORROBORATION, EXPLICITLY NOT AS RESOLUTION.** The open-year
> subset of [19] ends where this TS-6 Figure 38 surface ends, to within one of its
> own cells. That is consistent with both deriving from the same underlying ISA
> surface, and it is what "largely derived from TS-6" would predict. **It does not
> resolve the citation question:** [19] cites **"ISA, 2012"**, and [18] is **ISA
> Technical Study No. 6 (2010)** — different years on their face. "ISA, 2012" could
> be a later ISA publication reproducing the same surface, a different technical
> study, or a mis-citation. Two surfaces sharing an eastern limit is evidence of a
> shared source; it is not identification of that source.

**The citation question had no BACKLOG entry.** The task's premise said it "keeps its
BACKLOG entry" — there is none, anywhere in the repo. One is filed in this commit, so
this corroboration cannot later be mistaken for the resolution.

**Found in passing, flagged not fixed:** [19]'s queue row declares `is_open: true`,
but its own metadata says **426 of its 2,790 nodule-abundance rows come from
"proprietary information."** That is a live inconsistency in a field the licence
discipline reads. Not changed here — out of this task's scope — and BACKLOGged.
